## Phase 2B1A and Phase 2B1B frozen runtime contracts

`GET /api/v1/dashboard/summary` is implemented as Phase 2B1A and `GET /api/v1/devices/{id}/status` as Phase 2B1B. ASP.NET fixed route literals are case-insensitive, while the device-status ID remains strictly exact lowercase UUID-D; invalid noncanonical IDs, including an encoded slash when routing binds it as the raw `{id}` segment, are `400 invalid-device-status-id`; a single trailing slash is routing-equivalent to the device-status route, while additional path segments and other paths that do not structurally match remain `404`. Device-status accepts no query string. Its `lastReceivedAt` is exclusively the exact watermark ledger row's `received_at`, matched by watermark Agent ID, watermark Result ID, and current Probe ID; a missing or partial watermark model is sanitized `503 device-status-unavailable`. Both reads generate a server UUID-N correlation ID before authorization. Metrics, a status-enriched device list, history/timeline, audit reads, SignalR runtime, frontend behavior, WP-08 notification fan-out, and WP-09 reporting/retention remain outside the Phase 2B1 runtime slices. Incident reads and actions are frozen separately below as Phase 2B2 contracts only; their runtime remains unstarted.

Phase 2B1B requires the authenticated `dashboard.read` policy. A fresh lowercase UUID-N correlation ID is installed before authentication and authorization, and caller-supplied correlation or tracing values are never used in response headers, Problem Details, logs, or persistence. The raw route segment must equal its exact lowercase canonical UUID-D representation. An encoded slash is `400 invalid-device-status-id` when ASP.NET binds it into `{id}`; a single trailing slash invokes the same route, while extra segments and otherwise structurally unmatched paths remain route-level `404`. Any query parameter is `400 invalid-device-status-query`, and every `If-Match` value is `400 if-match-unsupported`, both before database access.

The device-status reader uses an explicit PostgreSQL `REPEATABLE READ` transaction with `AsNoTracking` reads and a bounded, constant query shape without per-Probe fetches. Effective status precedence is disabled Device or Probe, then active enabled Site/Device/Probe maintenance, then persisted projection visible status, with a missing projection yielding `Unknown`. Focused fixtures use the injected fixed evaluation clock to prove inclusive starts and exclusive ends. The watermark identity is exactly `AgentId + ResultId + current ProbeId`; `lastReceivedAt` comes only from the matching ledger row's `received_at`, never from another ledger row, heartbeat, event timestamp, or server time.

Missing projections return `Unknown`, version `0`, and null freshness, receipt, Agent, and incident fields. Missing or inconsistent watermark Agent/ledger data and response canonicalization/provider failures return sanitized `503 device-status-unavailable` Problem Details with only the frozen safe fields; the endpoint-local result never emits the framework-derived `traceId`. The unavailable event is emitted through a scope-isolated logger with EventId `7002`, fixed message, safe correlation only, and no exception or request properties. Caller cancellation aborts the request after read cleanup, without an unavailable response or event. Successful and failed reads are mutation-free, and canonical response bytes plus the strong SHA-256 ETag remain stable across equivalent requests and insertion order.

Both routes initially require the global authenticated `dashboard.read` scope. There is no site-grant model: optional `siteId` is a data filter only, never an authorization boundary. Both reads use a server-generated lowercase UUID-N correlation ID and never persist a caller-controlled correlation ID.

`DashboardSummaryResponse` has no `generatedAt` and neither route adds a request-time timestamp. `StatusEnrichedDeviceResponse` also has no request-time timestamp. Authoritative monitoring instants are UTC `Z`; client receipt time is presentation-only and never an authoritative monitoring timestamp.

Filters are optional. `siteId` is parsed as UUID-D and rendered lowercase. Non-null `area`, `deviceType`, `criticality`, and `tag` are trimmed, Unicode Form-C normalized, non-empty after normalization, and limited to 128 UTF-16 code units; exact enum tokens are `Unknown`, `Up`, `Degraded`, `Down`, `Recovering`, `Maintenance`, and `Disabled`. The response `appliedFilter` contains the single validated normalized filter representation (including explicit nulls), never the caller's unnormalized input. No other Unicode normalization is performed.

Visible status is contract-owned: disabled Device or Probe wins (`!Device.Enabled || !Probe.Enabled => Disabled`), then active matching maintenance (`Maintenance`), then persisted projection `VisibleStatus`. A missing projection is `Unknown`, state version `0`, and has nullable freshness, receipt, Agent, and incident fields; it must never become `Up`. UNKNOWN expiry may coexist with an active availability incident. An offline Agent is persisted `Agent.Status == Offline`; an active incident is `Open` or `Acknowledged`. `openIncidentId` is projection-authoritative; an incident row is a consistency check.

Summary always emits all seven status-count values in the exact order above. `recentlyDown` contains final visible `Down` rows with the active incident referenced by the projection; `sinceAt` is `availability_incidents.opened_at`, maximum 20, ordered `sinceAt DESC, probeId DESC`, with duplicate `probeId` rejected. `offlineAgents` contains persisted offline Agents referenced by a filtered projection `watermark_agent_id`, maximum 20, ordered `lastHeartbeatAt ASC NULLS FIRST, agentId ASC`, with duplicate `agentId` rejected. `openIncidents` contains Open/Acknowledged rows, maximum 20, ordered `openedAt DESC, incidentId DESC`, with duplicate `incidentId` rejected. UUID rendering and every tie-break use lowercase UUID-D and ordinal comparison.

The reusable contract canonicalizer validates the complete response before producing any bytes or ETag, then writes exact UTF-8 bytes for 200 responses. It writes object names in ascending ordinal order, writes every declared property including null, uses the collection orders above, exact PascalCase enum tokens, lowercase UUID-D, minimal base-10 integer JSON, System.Text.Json's fixed default escaping, and UTC `yyyy-MM-dd'T'HH:mm:ss.fffffffZ`. PostgreSQL timestamps are normalized to microsecond precision before DTO construction. Probes are sorted by lowercase `probeId` ordinal and duplicate IDs fail; tags are sorted ordinal and exact duplicates fail, while case-distinct tags remain distinct. Null collections/elements and invalid response values fail closed. The semantic summary lists and status counts are never re-sorted: they must already satisfy their frozen membership, cap, and order. The canonicalization marker is `wp07-2b1`; the strong identity-encoded response ETag is `"wp07-2b1-sha256-<43-character-unpadded-base64url-SHA256>"`, calculated from those exact bytes. Content type is `application/json; charset=utf-8`; no alternate representation or compression is permitted.

Both GET reads accept `If-None-Match` entity-tag lists across multiple header lines. Wildcard is valid only as the sole member. Supplied weak and strong tags use weak comparison for GET. Malformed input is `400` code `invalid-if-none-match`; a match is bodyless `304` with the current strong ETag, `Cache-Control: private, max-age=0, must-revalidate`, and `X-Correlation-ID`; a non-match is canonical `200`. `If-Match` is unsupported for these reads.

For `GET /api/v1/dashboard/summary`, invalid caller filters remain `400`. For `GET /api/v1/devices/{id}/status`, invalid route/query/header input retains its frozen `400` codes. A database/provider read failure or server-side response validation/canonicalization failure on either route is instead a sanitized `503 Service Unavailable` with the route's unavailable code and server-generated `X-Correlation-ID`; it never exposes internal exception, SQL, provider, entity, or stack details. Caller cancellation is preserved and is not translated to `503`.

## Phase 2B2 incident read/action contract (frozen; runtime not started)

Phase 2B2 Commit 1 freezes the following incident surface without adding routes, services, persistence, or runtime wiring:

| Operation | Contract |
| --- | --- |
| `GET /api/v1/incidents` | Cursor-paged incident list using the existing incident filter and ordering contract; no aggregate ETag. |
| `GET /api/v1/incidents/{id}` | Incident detail with a server-generated strong opaque `ETag` and `Cache-Control: private, max-age=0, must-revalidate`; supports `If-None-Match`. |
| `GET /api/v1/devices/{id}/incidents` | Cursor-paged device incident history with status/time filters and opened-at descending default order; no aggregate ETag. |
| `GET /api/v1/incidents/{id}/lifecycle-events` | Cursor-paged immutable lifecycle events ordered by occurrence time descending. |
| `GET /api/v1/incidents/{id}/comments` | Cursor-paged comments ordered by creation time descending. |
| `POST /api/v1/incidents/{id}/acknowledge` | Acknowledge an open incident. |
| `POST /api/v1/incidents/{id}/comments` | Add a comment; success is `201` with `IncidentCommentResponse`. |
| `POST /api/v1/incidents/{id}/resolve` | Manually resolve only when the underlying Probe status is neither `Down` nor `Recovering`. |

The incident detail ETag is server-generated, strong, quoted, opaque, and stable while incident identity and concurrency state are unchanged. Its encoding is not part of the contract. It appears only in the HTTP `ETag` header; no response body exposes `ETag` or `rowVersion`. Detail `If-None-Match` uses the same bounded entity-tag list parsing, weak comparison, wildcard, malformed-input, and empty-list-member rules as the Phase 2B1 conditional reads. A matching detail request returns bodyless `304` with `ETag`, the stated `Cache-Control`, and `X-Correlation-ID`. Phase 2B2 defines no aggregate ETag for list responses. [ADR-013 §5.1](../adr/ADR-013-wp07-phase2b2-incident-runtime.md#51-exact-incident-etag-v1-byte-encoding) freezes the internal incident ETag v1 canonical bytes and vectors; clients treat ETags as opaque. The current locked ETag is compared before state-conflict evaluation, exact stored response ETags replay without recomputation, and Commit 3C reads plus command runtime share one provider.

Every acknowledge, comment, and manual-resolution command requires exactly one strong `If-Match` entity tag. An absent header is `428 Precondition Required`; an empty or OWS-only header field value, malformed tag, weak tag, wildcard, comma-list, or multiple header values is `400 invalid-if-match`. The quoted empty opaque tag `""` is syntactically valid: it is current when it equals the current ETag and otherwise is a valid stale tag that returns `412 concurrency-conflict`, with the current ETag in both the `ETag` header and the `currentEtag` Problem Details extension. On a fresh command, receipt handling and all required locked reads precede the current-ETag comparison; that comparison precedes every command-state conflict, so a stale tag returns `412` even if the locked state would also return `409`. Exact replay still occurs before current-state reads. Successful acknowledge and manual resolution return `200 IncidentActionResponse`; comment creation returns `201 IncidentCommentResponse`. Each successful command returns the resulting incident ETag. Successful acknowledge, comment, manual resolution, and automatic resolution advance incident concurrency.

Every command also requires exactly one canonical lowercase UUID-D `Idempotency-Key`. An absent, empty, malformed, or repeated value is exactly `400 invalid-idempotency-key` before `If-Match`, body parsing, or database access.

After content-type validation and before DTO construction, each command body is
decoded with `new UTF8Encoding(false, true)` and parsed as JSON without any
replacement fallback. Malformed UTF-8; malformed or truncated escapes; a lone
or non-immediately-paired `\uD800`–`\uDBFF` high-surrogate escape; and a lone
`\uDC00`–`\uDFFF` low-surrogate escape are exactly `400 invalid-json` with
title `invalid-json` and detail `The request body is invalid.`. A correctly
paired high/low escape is one supplementary scalar. A supplementary scalar
written directly in the JSON string as its valid four-byte UTF-8 sequence is
also accepted, remains that same scalar through normalization, persistence,
v1 request fingerprinting, response representation, and replay, and counts as
two UTF-16 code units. A literal valid-UTF-8 U+FFFD remains a distinct scalar.
This staged failure returns safe server
correlation, exposes and logs neither request text nor parser details, and
executes zero database commands or mutations.

The unchanged request DTO metadata validates each raw acknowledgement comment, general comment, and `ResolveIncidentRequest.Note` as 1–2,000 UTF-16 code units before `.Trim()` is applied. The unchanged `[Required]` attribute rejects null, empty, and whitespace-only raw text at that DTO-validation stage; whitespace-only input never reaches trimming. Only after successful DTO validation is the value trimmed, then defensively required to remain non-empty and free of U+0000–U+001F, U+007F–U+009F, U+2028, and U+2029 before persistence. The scalar check returns `400 invalid-incident-text` before any database command, including for decoded JSON escapes. Raw 2,001-unit input fails before trimming even if its padding would reduce it below the limit. Trimming cannot increase length, so persisted normalized values remain at most 2,000 UTF-16 code units. DTO metadata is not changed.

An exact idempotency replay returns its original status, body, Content-Type, and ETag even if a later command has advanced the incident. After the full-key receipt read, replay also reads the immutable HumanPrincipal referenced by `receipt.actor_id` and verifies that its case-sensitive issuer/subject equals the authenticated identity before comparing the stored-version request fingerprint. This read-only verification never inserts, attaches, or mutates a principal and never reads mutable outcome, incident, projection, comment, lifecycle-action, or audit state. A different actor or fingerprint is `409 idempotency-key-reuse-conflict`; a missing/inconsistent principal mapping is a sanitized dependency failure. Reusing a key with a different route or incident is likewise the frozen conflict. Receipt retention is indefinite until WP-09/UA-09 defines a retention policy. Future receipts store `request_fingerprint_version = 1`, the exact length-prefixed v1 request digest, exact successful response status and UTF-8 body bytes, exact Content-Type and quoted ETag values, outcome kind, and command-specific outcome reference; they do not retain raw sensitive text unless strictly necessary. Deferred reciprocal composite foreign keys bind the receipt's `idempotency_key`, child ID, `incident_id`, actor/author identity, and lifecycle `outcome_kind = action_kind`; the child unique keys are `(idempotency_key, id, incident_id, author_id)` for comments and `(idempotency_key, event_id, incident_id, actor_id, action_kind)` for lifecycle actions. Persistence must support the full 2,000 UTF-16-code-unit comment and resolution-note limits.

Incident duration is `TotalDowntimeSeconds`, nullable. For a resolved incident it is the floor of `(resolvedAt - openedAt).TotalSeconds` over the half-open interval `[openedAt, resolvedAt)`. Zero is valid. UTC instants are required; `resolvedAt < openedAt` is invalid persisted state and is rejected rather than clamped. Open and Acknowledged incidents return null, and active duration is never calculated from server/request time. Acknowledgement, comments, occurrences, maintenance, and status overlays do not pause or reset the interval.

Public `AcknowledgedBy` and `ResolvedBy` remain nullable surrogate UUIDs because engine-driven lifecycle states have no human actor. `IncidentLifecycleResponse.ActorId` is nullable only because WP-06 engine lifecycle rows have no actor; every WP-07 public lifecycle-action row has a required non-null surrogate `actor_id`. `IncidentCommentResponse.AuthorId` and `incident_comments.author_id` are required, non-null surrogate UUIDs. The mapping key is the exact authenticated, non-empty, bounded OIDC `iss` + `sub` pair, uniquely mapped to an internal surrogate UUID; email, display name, role, `NameIdentifier`, and `Guid.Empty` are never fallbacks. Issuer, subject, tokens, authorization values, and mapping internals are not exposed or logged.

Incident reads use `incidents.read` for Viewer, Operator, Engineer, Administrator, and Auditor. Acknowledge, comment, and manual resolution use `incidents.operate` for Operator and Administrator. The existing role matrix is unchanged. With a current tag, manual resolution while the underlying Probe status is `Down` or `Recovering` returns `409 incident-manual-resolution-state-conflict`, includes the unchanged ETag in the header and `currentEtag` extension, and makes no incident, projection, lifecycle, comment, audit, principal, or receipt mutation. A fresh successful manual resolution clears the locked projection's `open_incident_id`, advances its `state_version` exactly once, and leaves underlying/visible status, counters, and watermarks unchanged; replay never applies that mutation again.

### Phase 2B2 Commit 3 design freeze and Commit 3A persistence foundation

[ADR-013](../adr/ADR-013-wp07-phase2b2-incident-runtime.md) accepts and freezes the documentation-only runtime design for all eight incident routes. Replay and conflict use no save or commit. Receipts store `request_fingerprint_version = 1` and the exact length-prefixed v1 SHA-256 input frozen in ADR-013. Public lifecycle `action_kind`/`reason_code` pairs are exactly `acknowledgement`/`operator-acknowledgement` and `manual_resolution`/`manual-resolution`; they map to response `Type`/`ReasonCode` values `acknowledged`/`operator-acknowledgement` and `manually-resolved`/`manual-resolution`. Lifecycle union source ranks are engine `0` and public action `1`.

For matched protected routes, authentication and authorization precede endpoint validation and body parsing. On a command route after role authorization, `PrincipalIdentityResolver` must resolve exactly one valid case-sensitive `iss` and `sub`; failure is `403 invalid-incident-actor-identity`, before all endpoint input and database work. Authorized command input precedence is then forbidden/unrecognized query, canonical route, applicable Idempotency-Key, applicable conditional header, content type, strict UTF-8/JSON/surrogate decoding (`400 invalid-json`), DTO annotations including raw `[Required]` and length, normalized scalar semantics, then database access. Inapplicable stages are omitted without reordering; the earliest simultaneous failure alone is returned. The disposable non-UTF8 fixture uses Testcontainer `postgres` administration on the `postgres` maintenance database, non-transactional create/drop, `Pooling=false` for every fixture-targeting connection, and mandatory administrative cleanup after normal and failing assertions. ## 1. Boundaries and compatibility

A response must not invent current status, metrics, or live data when its backing source is unavailable.

### Pagination, filtering and sorting

Existing collection endpoints retain `page`/`pageSize` (default 1/50; maximum 200). New history, incidents, comments, and audit lists use opaque cursor paging: `pageSize` default 50/max 200 and `nextCursor`; an absent cursor begins the query. Cursor payloads bind the normalized filters and sort so reuse with changed criteria returns `400` `cursor-filter-mismatch`.

All filter names are explicit and case-insensitive only where documented: UUIDs, exact status enums, `siteId`, `deviceId`, `probeId`, `area`, `deviceType`, `criticality`, `tag`, `openedFrom`, `openedTo`, `from`, `to`, `action`, `entityType`, `entityId`, and `actorId`. Time bounds are inclusive UTC instants. Incident ordering is `openedAt desc,id desc` by default; timeline/audit ordering is `occurredAt desc,id desc`; every alternate direction retains `id` as its tie-breaker.

## 4. Status, dashboard and chart semantics

Visible status vocabulary is exactly `Unknown`, `Up`, `Degraded`, `Down`, `Recovering`, `Maintenance`, `Disabled`. `DeviceStatusResponse` exposes both visible and underlying status, `stateVersion`, `lastFreshEventAt`, receipt time, current Agent identity, and open-incident reference. Summary counts count Probes, not Devices; a Device with multiple Probes retains one status item per Probe.

Metrics accepts only bounded UTC ranges: 1 hour, 6 hours, 24 hours, 7 days, or a custom range no greater than 31 days. `resolution=auto|raw|minute|fiveMinutes|hour`; the server selects and returns each series' effective resolution. The implementation phase must publish its maximum point count before enabling `raw`. Points are ordered ascending, use UTC instants, preserve null RTT for failed attempts, and never turn missing intervals into zero values. Missing intervals render as chart gaps. `isPartial=true` plus a stable `partialErrorCode` means some series/source data could not be returned; an unavailable entire metrics dependency is `503` Problem Details, not an empty successful series.

## 5. Timezone, stale data and caching

Storage, event processing, query bounds, cursor ordering, audit, and SignalR payloads remain UTC. The display timezone precedence is: persisted user override, selected Site IANA timezone, then browser timezone. Ambiguous daylight-saving local times display their UTC offset; custom-range inputs are converted to UTC before transmission.

### Frozen timezone-preference contract (implemented in Phase 2A)

The eventual implementation retains at most one global PostgreSQL row for each authenticated human principal after its first state-changing write. Its identity key is exactly the explicit authenticated `iss` plus `sub` claim pair. Both are required, non-empty, and at most 512 Unicode scalar values (PostgreSQL characters/code points). Email, display name, role, `NameIdentifier`, and `Guid.Empty` are never fallbacks; missing either claim fails closed. Development authentication will supply constant issuer `https://ee-pulse.invalid/development` and a stable canonical synthetic subject derived from `X-EE-Pulse-Actor`. Production endpoints remain unavailable to identities without explicit issuer and subject claims.

The sole preference field is nullable `timezone`. `GET /api/v1/users/me/timezone-preference` is read-only and never creates a row. With no row it returns HTTP 200, `{ "timezone": null, "etag": "\"tz-0\"" }`, and `ETag: "tz-0"`. The no-row ETag is therefore exactly `"tz-0"`. A retained row has monotonically increasing positive version `n` and exactly `ETag: "tz-n"`; this cannot collide with `"tz-0"`. Response-body `etag` and response-header `ETag` are byte-identical. GET supports `If-None-Match`; a 304 includes the current ETag. The generated OpenAPI documents the conditional request header, strong ETag response header, server-controlled `X-Correlation-ID`, and 200/304/400/401/403 outcomes.

`PUT /api/v1/users/me/timezone-preference` requires exactly one strong `If-Match` value. Missing is 428. Malformed, weak, wildcard, empty, comma-list, or multi-value `If-Match` is HTTP 400 with code `invalid-if-match`. A syntactically valid but non-current tag is HTTP 412 with code `concurrency-conflict` and the current ETag. The first non-null write requires `If-Match: "tz-0"` and atomically inserts issuer, subject, canonical timezone, and version 1. A concurrent insert conflict re-reads current state and returns that 412 response; it never overwrites the winner.

`null` clears a persisted override by retaining its row, writing null timezone, and incrementing version. Rows are never deleted, preventing ABA; re-setting after a clear increments the retained version again. PUT of the same canonical timezone with the current ETag is an idempotent no-op: no version increment and no audit event. PUT null against absent `"tz-0"` is also a no-op: it creates no row and returns `"tz-0"`. The first non-null write atomically persists the preference and its redacted audit event; all other state-changing writes do the same. Audit metadata contains only operation and resulting version. The API emits one safe server-generated lowercase UUID-N correlation ID per request and reuses it in the response and audit event without persisting caller-controlled correlation, trace, or identity values.

Timezone values are validated and normalized by the reusable contract-level TZDB mechanism, backed by the NodaTime 3.3.3 embedded catalog, never the host operating-system catalog. It accepts canonical IANA IDs and recognized TZDB aliases, case-sensitively, and persists/returns only the canonical ID. The pinned provider canonicalizes `UTC` to `Etc/UTC`. Windows IDs, unknown IDs, empty or whitespace values, case-modified IDs, malformed/path-like inputs, and backslash-separated values are rejected; null remains valid only for clearing.

Timezone preference is personal settings data. Emit an audit event only for a successful state-changing create, update, or clear. Its metadata may contain operation type and resulting version only; it must not contain timezone values, issuer, subject, email, display name, authorization headers, or tokens. Logs must likewise omit raw identity tokens and unnecessary profile data. Phase 2A implements the PostgreSQL table/model/migration, repository transaction boundary, endpoint, authorization, and integration coverage for this contract. The Phase 2A timezone-preference endpoint does not claim dashboard/status data, incident actions, audit listing, SignalR runtime, or frontend behavior.

Every screen has distinct loading, empty, stale-data, partial-error, and permission-denied states. A successful stale cached response is labelled with `generatedAt`/last-refresh time. Summary and status reads support ETags derived from stable query/result versions. Clients send `If-None-Match`; `304` preserves cached data. Mutating commands require `If-Match` with the incident ETag; absent is `428`, stale is `412` with Problem Details code `concurrency-conflict` and the current ETag. Existing inventory row-version behavior remains unchanged.

## 6. Phase 2B2 incident actions and exact invalid-resolution conflict

The Phase 2B2 contract freezes these commands; runtime implementation remains pending:

- `POST /api/v1/incidents/{id}/acknowledge` with `AcknowledgeIncidentRequest`.
- `POST /api/v1/incidents/{id}/comments` with `AddIncidentCommentRequest`.
- `POST /api/v1/incidents/{id}/resolve` with `ResolveIncidentRequest`.

All require `incidents.operate`, a valid `PrincipalIdentityResolver` issuer/subject result, non-empty normalized text whose raw value first passed unchanged `[Required]` and the 1–2,000 UTF-16-code-unit DTO bound, exactly one strong `If-Match`, and a UUID `Idempotency-Key` header. Missing, empty, malformed, or repeated Idempotency-Key is `400 invalid-idempotency-key`; invalid command identity is `403 invalid-incident-actor-identity`; both precede body parsing/database access according to ADR-013. Runtime persistence uses one explicit transaction, a first `SaveChangesAsync` for state/child/audit while no new receipt is tracked, a second `SaveChangesAsync` for the fully populated version-1 receipt inserted last, and one `CommitAsync`. Pre-COMMIT failures and server-rejected deferred constraints roll everything back; a transport/cancellation failure after `COMMIT` is issued but before confirmation is indeterminate, returns the sanitized failure/cancellation behavior, and is resolved by same-key retry. Retrying the same route, incident, key, actor, and canonical request returns the original status, body, Content-Type, and ETag even if a later command advanced the incident; reuse of the key with a different route, incident, actor, or canonical request returns `409` `idempotency-key-reuse-conflict`. After all required locked reads on a fresh command, stale ETag `412` takes precedence over every state-conflict `409`. With a current tag, acknowledge is valid only for an open incident and otherwise returns `409` `incident-action-state-conflict`; comments are valid for active or resolved incidents and return `201`; successful acknowledgement/manual resolution return `200` `IncidentActionResponse`. Acknowledgement stores `action_kind = 'acknowledgement'`, `reason_code = 'operator-acknowledgement'` and returns lifecycle `Type = "acknowledged"`, `ReasonCode = "operator-acknowledgement"`; manual resolution stores `action_kind = 'manual_resolution'`, `reason_code = 'manual-resolution'` and returns lifecycle `Type = "manually-resolved"`, `ReasonCode = "manual-resolution"`. General comments create no lifecycle-action row. Every successful command records the action-specific append-only audit event in the same transaction once runtime is implemented. Receipt retention is indefinite until WP-09/UA-09 defines the policy, and receipts store the exact v1 fingerprint version/digest, exact successful response status and UTF-8 body bytes, exact Content-Type and quoted ETag values, outcome kind, and command-specific outcome reference rather than raw sensitive text unless strictly necessary.

Manual resolution is forbidden while the current underlying Probe status is `Down` or `Recovering`. When the supplied tag is current, the frozen contract specifies HTTP `409 Conflict`, standard Problem Details with type/code `incident-manual-resolution-state-conflict`, title `Manual resolution is not currently allowed`, and extensions `incidentId`, `probeId`, `underlyingStatus`, `visibleStatus`, `stateVersion`, and `currentEtag`. The unchanged current ETag is returned in the `ETag` header and `currentEtag` extension. It makes no incident, projection, lifecycle, comment, audit, principal, or receipt mutation. A stale tag instead returns `412 concurrency-conflict`. On fresh success the locked projection's `open_incident_id` becomes null and `state_version` advances exactly once; underlying/visible status, counters, and watermarks do not change. Exact replay, cancellation, failure, and rollback never apply or repeat that projection mutation. The client refetches incident and device-status queries, announces the reason, and keeps the resolve action unavailable until the state permits it. Confirmed recovery remains the normal automatic resolution route.

## 7. Audit and maintenance

`GET /api/v1/audit-events` is restricted to Auditor and Administrator. It returns metadata only—before/after JSON is not exposed by this WP-07 contract—and supports action/entity/actor/time filters and deterministic cursor paging. Incident mutations create append-only audit events with actor, entity, correlation ID, timestamp, and redacted action metadata.

The existing maintenance endpoints are reusable for CRUD. A later additive list contract must support scope (`siteId`, `deviceId`, `probeId`) and active/range filtering before a complete maintenance page is claimed.

## 8. SignalR invalidation and refresh policy

The proposed authorized hub is `GET/WS /hubs/dashboard`; it is not implemented in Phase 1. Connection authorization uses the same authenticated user principal and applies read-policy scope before subscription. Clients do not send arbitrary group names. Server grouping, if required, is derived only from validated Site/device scope.

The sole initial payload shape is `DashboardInvalidationEvent` with schema version 1 and event types `status.changed`, `incident.changed`, `agent.changed`, and `maintenance.changed`. Payloads contain only identifiers, optional version, and UTC occurrence time—not metrics, comments, credentials, or unrestricted inventory fields. On receipt, clients invalidate/refetch the corresponding TanStack Query keys; they do not merge aggregate state locally.

Clients reconnect with bounded exponential backoff and jitter. On successful reconnect they refetch every visible dashboard, device, incident, Agent, and maintenance query. While disconnected they refresh visible queries every 30 seconds. While connected, including NOC/TV mode, they perform a 60-second safety refresh. NOC mode never suppresses the disconnected cadence. Reconnection and refresh failures surface stale/partial-error state without fabricating data.
