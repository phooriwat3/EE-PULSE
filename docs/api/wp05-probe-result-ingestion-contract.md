# WP-05 Probe-result ingestion contract

Status: Proposed - design only
Date: 2026-08-20 (Asia/Bangkok)
Owner: Lead/Integration Agent

## Scope and compatibility

This is the proposed additive contract for delivery of immutable WP-04 results. It is not generated OpenAPI and does not change the frozen WP-03 or WP-04 contracts. `resultSchemaVersion` and the HTTP/API version are independently versioned: compatible fields may be added; removed, reinterpreted, or required fields require a new explicit version and consumer review.

## Identity and payload

Each persisted record has one immutable `resultId` (UUID) generated by the Agent. Its deduplication key is `(agentId, resultId)`; `batchId` is an ephemeral request identifier only and is never a substitute for result identity.

```text
ProbeResultEnvelope v1
  resultSchemaVersion: 1
  resultId: UUID
  agentId: UUID
  probeId: UUID
  configurationVersion: int64
  startedAt: RFC 3339 UTC
  endedAt: RFC 3339 UTC
  attemptCount: integer
  successfulAttemptCount: integer
  packetLossRatio: decimal [0,1]
  minRttMilliseconds: decimal|null
  averageRttMilliseconds: decimal|null
  maxRttMilliseconds: decimal|null
  errorCategory: WP-04 fixed category|null
```

`agentId` comes from the authenticated Agent identity and must equal the body value. `probeId` and `configurationVersion` must be valid for that Agent's acknowledged configuration lineage. The Backend retains the supplied version even when a newer configuration exists; version mismatch is not silently rewritten. Unknown schema versions, malformed immutable fields, or identity mismatch are permanent per-record rejections.

## Proposed ingestion boundary

`POST /api/v1/agents/{agentId}/result-batches` accepts one authenticated batch with a new `batchId`, at most 1,000 envelopes and at most 1 MiB serialized request payload (the smaller limit wins). The endpoint is deliberately proposed only; route, authorization, DTO, and OpenAPI changes require the ownership protocol in [repository ownership](../repository-ownership.md).

The Backend validates request bounds and authentication, then processes every envelope idempotently in PostgreSQL. A committed record is either newly accepted or an existing matching deduplication record. A same key with unequal immutable content is a security/integrity failure, is not acknowledged, and is logged only with safe identifiers.

The response returns the request `batchId`, an explicit accepted `resultId` set, and explicit permanent-rejection entries containing `resultId` plus a stable, non-secret reason code. It may return a bounded retry-after hint for whole-batch transient failures. Acknowledgement is per result, not an implied success for the request.

## Acknowledgement and checkpoint semantics

The Agent must mark only results named accepted by a validated response as acknowledged in one SQLite transaction; acknowledged results are not redelivered and are physically removed only by the documented cleanup process within 24 hours. It moves a permanently rejected result to a durable local quarantine in the same SQLite transaction as removal from the pending queue, preserving its identity, sanitized reason code, and payload for operator recovery. No response, malformed response, partial response, 401/403/410, or retryable status advances the checkpoint.

The normal sender takes the earliest pending records first. Quarantining a permanently rejected record unblocks later FIFO records without discarding evidence. Acknowledged records may be selected for cleanup only if the exact row identity is acknowledged; implementation may additionally maintain a contiguous diagnostic checkpoint, but it must not treat it as authority over individual acknowledgements.

## Retry, offline, and authentication behavior

- Retryable conditions are connection/DNS failures, timeouts, 408, 429, and 5xx. Use bounded exponential delay with full jitter, a configured minimum/maximum, and a reset only after a confirmed acknowledgement.
- 401/403 triggers the existing credential/configuration recovery path and preserves all pending rows. 410 marks the Agent revoked per WP-03 and stops delivery; it does not delete buffered results.
- Offline mode continues transactional local enqueue until the approved hard threshold: 95% of the 5 GB default quota or breach of the greater-of-2-GB-or-10%-volume reserve. At that point it stops new result production and scheduling, while delivery and recovery continue; it resumes automatically only below 70% of quota and after the reserve is restored. It neither creates synthetic results nor replays missed WP-04 schedule slots.
- At 80% of quota the Agent reports degraded storage health. Acknowledged rows may be cleaned up within 24 hours; unacknowledged rows are never age-deleted, and silent result loss is prohibited.
- Logs and metrics contain only Agent/Probe/result identifiers, fixed outcome/reason categories, counts, age, byte totals, and retry bands. They exclude bearer tokens, credential material, raw request bodies, target addresses, exception text, and unbounded response values.

## Backend ownership and projection

PostgreSQL owns the immutable accepted-result ledger, request deduplication, validation outcome, and projection state. VictoriaMetrics receives only a bounded-label metric projection from committed PostgreSQL records. A VictoriaMetrics write failure marks that projection retryable; it cannot revoke the Backend acknowledgement or create another result ledger row. Status, incidents, notification intent, and user-facing query behavior are explicitly deferred to later work packages.
